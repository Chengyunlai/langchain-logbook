# 本地 Markdown 任务跟踪约定

本项目把大型课程改造、研究结论和实现任务保存在 `.scratch/` 中。这样做的目的，是让计划、依赖关系、决策依据和验收结果与代码一起版本化，同时避免把尚未稳定的内部规划发布为远程 Issue。

## 目录约定

- 每项大型工作使用一个独立目录：`.scratch/<effort>/`。
- 总地图使用 `.scratch/<effort>/map.md`。
- 子任务使用 `.scratch/<effort>/issues/<NN>-<slug>.md`，编号从 `01` 开始。
- 如需形成正式需求文档，使用 `.scratch/<effort>/PRD.md`。

## 普通任务约定

每个任务至少包含以下信息：

- `Status`：当前执行状态。
- `Triage`：任务适合由 Agent 独立执行、需要用户补充信息，还是需要人工参与。
- `Type`：`research`、`prototype`、`grilling` 或 `task`。
- `Blocked by`：前置任务编号；为空表示当前可执行。
- `Why`：为什么需要这项工作，以及它与最终学习目标的关系。
- `Question` 或 `Work`：需要解决的问题或需要交付的工作。
- `Acceptance`：完成后必须满足的可验证条件。
- `Answer`：研究结论、实现结果和验证证据；只在解决任务时填写。

## Wayfinder 操作

- **地图**：`.scratch/<effort>/map.md`，记录目的地、执行原则、已确认决策和仍处在迷雾中的问题。
- **子任务**：`.scratch/<effort>/issues/NN-<slug>.md`。
- **阻塞关系**：使用 `Blocked by: NN, NN`。列出的任务全部解决后，当前任务才进入可执行前沿。
- **前沿任务**：状态为 `open`、没有未解决阻塞项、尚未被认领的任务；编号最小者优先。
- **认领**：执行前先把 `Status` 改为 `claimed`，避免并发重复工作。
- **解决**：追加 `## Answer`，写明结论、改动、验证和遗留风险；然后把 `Status` 改为 `resolved`，并在地图的“已确认决策”中增加一条链接摘要。
- **新增任务**：只有在问题已经足够明确、能够写出验收标准时才创建；仍不清晰的内容保留在地图的“尚未明确”中。

## 中文解释要求

所有面向学习者或维护者的任务说明、研究结论、架构决策和验收说明必须使用中文。代码标识符和官方英文术语可以保留，但首次出现时要解释其中文含义、适用边界和常见混淆点。
